# Recommendation System Specification

## 1. Overview

The recommendation system provides article recommendations using a hybrid approach combining vector similarity, title matching, view history, and popularity metrics. A request with tracking consent is personalized for exactly one recommendation subject (section 3.1): the authenticated registered user if the request is authenticated, otherwise the consented anonymous device. A request without a recommendation subject receives public recommendations, and the system reads or writes no subject-specific Redis key for it. No recommendation request SHALL read private library tables.

## 2. Components

### 2.1 Vector Service

The `EmbeddingService` interfaces with ChromaDB for vector-based similarity search.

The service SHALL call `ChromaClient.getOrCreateCollection` with `embeddingFunction=null` and `configuration={ hnsw: { space: 'cosine' } }`. The Chroma JavaScript client SHALL NOT generate embeddings. Every vector upsert and vector query SHALL provide embeddings generated by the configured LLM embedding scenario.

#### getVector(articleId: string): Promise<number[] | null>

1. If Chroma is disabled (`config.chroma.enable = false`), return `null` without a Chroma request.
2. Load the collection and query Chroma for `ids = [articleId]` with `include = ['embeddings']`, both inside error handling and a 3000 ms read timeout.
3. Return the embedding vector if it is a non-empty array; otherwise return `null`.
4. If loading the collection or the query fails or times out, log the error and return `null`.

#### getVectors(articleIds: string[]): Promise<Map<string, number[]>>

1. If Chroma is disabled or `articleIds` is empty, return an empty map without a Chroma request.
2. Otherwise issue exactly one Chroma `get` request with `ids = articleIds` and `include = ['embeddings']`, bounded by a 3000 ms read timeout.
3. Return a map from each returned vector ID to its non-empty embedding array. An ID without a stored non-empty vector is absent from the map.
4. If loading the collection or the request fails or times out, log the error and return an empty map.

#### getNearestVectors(embedding: number[], n: number, where?): Promise<QueryResult>

1. If Chroma is disabled, return empty results `{ ids: [[]], distances: [[]] }`.
2. If embedding is empty, return empty results.
3. Query Chroma for n nearest neighbors.
4. If `where` is provided, pass it to Chroma as a metadata filter.
5. Return IDs and distances.

#### getNearestArticleCandidates(embedding, distinctArticleLimit, rawVectorLimit)

1. Query Chroma for at most `rawVectorLimit` summary and chunk vectors.
2. Fold vector hits by metadata `articleId`; if metadata is absent, use the prefix before `:chunk:` or the whole vector ID.
3. For each article, keep the vector hit with the maximum score `max(0, 1 - distance)`.
4. Return at most `distinctArticleLimit` distinct articles sorted by descending vector score.
5. Each returned hit SHALL include `id`, `score`, `distance`, `vectorId`, `vectorKind`, and optional `chunkIndex`, `chunkStart`, `chunkEnd`, and `chunkText`.

#### getNearestArticleIdsBatch(embeddings, distinctArticleLimit): Promise<string[][]>

1. Return an array aligned 1-to-1 with `embeddings`.
2. If Chroma is disabled, `embeddings` is empty, or `distinctArticleLimit <= 0`, return empty arrays without a Chroma request.
3. Filter `embeddings` to valid non-empty vectors; if none are valid, return empty arrays without a Chroma request.
4. Issue exactly one Chroma `query` request passing all valid vectors in `queryEmbeddings`, `nResults = distinctArticleLimit`, `where = { $and: [{ deleted: false }, { kind: 'summary' }] }`, and `include = ['metadatas']`, bounded by a 3000 ms read timeout. Chunk vectors and vector documents SHALL NOT be requested.
5. For each query row, map each vector hit to its article ID by the rule of `getNearestArticleCandidates` step 2 and return the distinct article IDs in nearest-first order, truncated to `distinctArticleLimit`.
6. A returned ID is never a chunk vector ID (an ID containing `:chunk:`).
7. If loading the collection or the query fails or times out, log the error and return empty arrays.

#### getNearestArticleIds(embedding, distinctArticleLimit): Promise<string[]>

1. Delegate to `getNearestArticleIdsBatch([embedding], distinctArticleLimit)` and return the first result array (or `[]`).

#### upsertVector(id, metadata, document, embedding)

1. If Chroma is disabled, perform no write.
2. If Chroma is enabled, upsert one vector with the provided `id`, `metadata`, `document`, and `embedding`.

#### upsertArticleEmbeddings(article, summaryEmbedding?, chunkEmbeddings?)

1. Delete existing chunk vectors for `article.id`.
2. Upsert one summary vector with ID equal to `article.id`, metadata `articleId=article.id`, and metadata `kind="summary"`.
3. Split `article.content` into chunks of `config.chroma.chunkSize` characters with `config.chroma.chunkOverlap` overlap.
4. Upsert one chunk vector per chunk with ID `${article.id}:chunk:${index}`, metadata `articleId=article.id`, `kind="chunk"`, `chunkIndex`, `start`, and `end`.

#### rebuildArticleEmbeddings(batchSize = 20, concurrency = 5)

1. Load non-deleted articles in ascending article ID order in batches of `batchSize`.
2. For each article, generate one summary embedding from `article.summary` if non-empty after trimming; otherwise from `article.content`.
3. For each article, split `article.content` into chunks of `config.chroma.chunkSize` characters with `config.chroma.chunkOverlap` overlap and generate one embedding per chunk.
4. Upsert all generated summary and chunk vectors into Chroma with article metadata `{ title, authorId, category, tags }` plus vector-level metadata. The Chroma metadata field `tags` SHALL be a comma-separated string built from `article.tags`.
5. Process at most `concurrency` articles at the same time inside each batch.
6. Continue after per-article failures.
7. Return `{ processed, updated, failed, failedArticleIds }`.

### 2.2 Recommendation Service

The `RecommendationService` provides recommendation algorithms.

## 3. Recommendation Subjects and Behavior Tracking

### 3.1 Recommendation Subject

`RecommendationSubject` is exactly one of:

- `{ kind: 'user', userId }`, where `userId` is the authenticated `registered_user.id` (`ctx.user.id`). It is never `luoguUid`.
- `{ kind: 'device', deviceId }`, where `deviceId` is the `X-Device-Id` request header value.

`getConsentedDeviceId(ctx)` returns the `X-Device-Id` header value if and only if `X-Consent-Tracking` is exactly `true` and `X-Device-Id` is a string matching `/^[A-Za-z0-9._-]{1,64}$/`; otherwise it returns `null`.
`resolveRecommendationSubject(ctx)`:

1. If `X-Consent-Tracking` is not exactly `true`, return `null`.
2. If `ctx.user.id` is defined, return `{ kind: 'user', userId: ctx.user.id }`. The user role is not inspected.
3. If `getConsentedDeviceId(ctx)` is non-null, return `{ kind: 'device', deviceId }`.
4. Otherwise return `null`.

The tracking middleware and `GET /plaza/get` SHALL use `resolveRecommendationSubject` as the only rule that selects a subject.

### 3.2 Subject Storage

Every key below is a Redis sorted set with score = Unix timestamp in milliseconds and member = article ID.

| Subject  | Behavior key               | Recommended key                   | `maxCount`                                 | Behavior TTL (seconds)                       |
| -------- | -------------------------- | --------------------------------- | ------------------------------------------ | -------------------------------------------- |
| `device` | `anon_behavior:{deviceId}` | `anon_recommendations:{deviceId}` | `config.recommendation.anonymous.maxCount` | `config.recommendation.anonymous.expireTime` |
| `user`   | `user_behavior:{userId}`   | `user_recommendations:{userId}`   | `config.recommendation.maxHistory`         | `config.recommendation.user.expireTime`      |

Every recommended key has TTL 10800 seconds (3 hours).

### 3.3 recordBehavior(subject, articleId)

1. Add `(timestamp, articleId)` to the subject's behavior key.
2. Trim the set to keep only the most recent `maxCount` entries of the subject.
3. Set the key TTL to the subject's behavior TTL.
4. Steps 1 through 3 execute in one Redis transaction.
5. A Redis error is logged and not thrown.

### 3.4 recordRecommendedArticles(subject, articleIds)

1. Add all article IDs with the current timestamp to the subject's recommended key.
2. Trim the set to the subject's `maxCount` entries.
3. Set the key TTL to 10800 seconds.
4. If `articleIds` is empty, no Redis command is executed.
5. Steps 1 through 3 execute in one Redis transaction.
6. A Redis error is logged and not thrown.

### 3.5 getRecommendedArticles(subject)

Return all article IDs from the subject's recommended key. On a Redis error, log the error and return an empty array.

### 3.5.1 getBehaviorEntries(subject)

Return the subject's `maxCount` most recent `{ articleId, timestamp }` entries ordered by descending timestamp from the subject's behavior key. On a Redis error, log the error and return an empty array.

### 3.6 mergeDeviceHistory(deviceId, userId)

For each pair `(source, destination, maxCount, ttl)` below, in this order:

1. `(anon_behavior:{deviceId}, user_behavior:{userId}, config.recommendation.maxHistory, config.recommendation.user.expireTime)`
2. `(anon_recommendations:{deviceId}, user_recommendations:{userId}, config.recommendation.maxHistory, 10800)`

the system SHALL execute one Redis Lua script that atomically performs:

1. If `source` does not exist, return without writing any key.
2. Set `destination` to the union of `destination` and `source`; a member present in both keeps the greater score.
3. Trim `destination` to the most recent `maxCount` entries.
4. Set the `destination` TTL to `ttl` seconds.
5. Delete `source`.

Postconditions: after a call without Redis errors, neither source key exists, and a repeated call with the same arguments writes no key. A Redis error is logged and not thrown.

## 4. User Profile Vector

### 4.1 drawProfile(articles: string[]): Promise<number[]>

Compute a decay-weighted, L2-normalized centroid vector from a list of article IDs ordered newest first.

**Algorithm:**

```
1. Fetch all embeddings with exactly one EmbeddingService.getVectors(articles) call.
2. validVectors = non-empty embeddings of articles, in input order, whose length equals the first valid embedding's dimension d.
3. If validVectors is empty, return empty array.
4. Initialize profile = zero vector of dimension d, weightSum = 0, factor = 1.
5. For each vector in validVectors:
   a. profile += vector * factor
   b. weightSum += factor
   c. factor *= config.recommendation.decayFactor
6. Divide each component of profile by weightSum.
7. Compute norm = sqrt(sum(profile[j]^2)). If norm > 0, divide each component of profile by norm.
8. Return profile.
```

### 4.1.1 drawInterestProfiles(articles: string[], maxClusters = 3, similarityThreshold = 0.65): Promise<Array<{ vector: number[]; weight: number }>>

Partition a subject's recent viewed articles into at most `maxClusters` L2-normalized interest centroids using one `EmbeddingService.getVectors(articles)` call.

**Algorithm:**

```
1. Fetch all embeddings with exactly one EmbeddingService.getVectors(articles) call.
2. validVectors = non-empty embeddings of articles, in input order, whose length equals the first valid embedding's dimension d.
3. If validVectors is empty, return empty array.
4. Initialize empty cluster list and factor = 1.
5. For each vector in validVectors:
   a. Find the existing cluster whose current sum vector has the maximum cosine similarity to vector.
   b. If such a cluster exists and (bestSimilarity >= similarityThreshold OR clusters.length >= maxClusters):
      add vector * factor to that cluster's sum and add factor to that cluster's weight.
   c. Otherwise append a new cluster with sum = vector * factor and weight = factor.
   d. factor *= config.recommendation.decayFactor
6. For each cluster, divide sum by its L2 norm (discarding zero-norm clusters) to produce `{ vector, weight }`.
7. Return clusters sorted by weight descending.
```

### 4.2 selectProfileArticles(entries, limit): string[]

Input: entries `{ articleId, timestamp }` with timestamps in milliseconds.

1. Sort entries by `timestamp` descending; entries with equal timestamps keep input order.
2. Keep the first occurrence of each `articleId`.
3. Return the first `limit` article IDs.

## 5. API Endpoints

### 5.1 GET /plaza/get

Get personalized recommendations for the plaza page.

**Request:**

- Query parameter: `count` (number, optional) - Number of recommendations. Default 10; clamped to `[1, 50]`.
- Query parameter: `exclude` (string, optional) - Comma-separated article IDs that must not appear in the response. Empty IDs are ignored. Duplicate IDs are removed in first-seen order. At most the first 200 unique IDs are used.
- Header: `Authorization` (string, optional) - Bearer token resolved into `ctx.user` by the authorization middleware.
- Header: `X-Consent-Tracking` (string, optional) - If the value is exactly `true`, the request may be personalized.
- Header: `X-Device-Id` (string, optional) - Anonymous device identifier matching `/^[A-Za-z0-9._-]{1,64}$/`. This header is used only when `X-Consent-Tracking` is exactly `true`.

**Behavior:**

1. Parse `count` and `exclude`.
2. Let `subject = resolveRecommendationSubject(ctx)`.
3. If `subject` is `null`, respond with `getPublicRecommendations(count, excludedArticles)`.
4. If `subject.kind = 'user'` and `getConsentedDeviceId(ctx)` returns a device ID, complete `mergeDeviceHistory(deviceId, subject.userId)` before step 5.
5. Respond with `getPersonalizedRecommendations(subject, count, excludedArticles)`.
6. On any unhandled error, log the error and respond with code `500` and message `Failed to retrieve recommendations`.

**Response:**

- 200: Array of recommended articles with `reason` field. The endpoint has no authenticated-user-specific error response.
- 500: Generic error response on unexpected server failure; internal error details SHALL NOT be exposed.

**Response Fields per Article:**

| Field          | Type                             | Description                                                                                  |
| -------------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| `id`           | string                           | Article ID                                                                                   |
| `title`        | string                           | Article title                                                                                |
| `summary`      | string                           | Trimmed `article.summary` if non-empty, else content preview; truncated to 100 Unicode chars |
| `author`       | User                             | Author information                                                                           |
| `updatedAt`    | Date                             | Last update timestamp                                                                        |
| `category`     | number                           | Article category                                                                             |
| `tags`         | string[]                         | Article tags                                                                                 |
| `reason`       | string                           | Recommendation source                                                                        |
| `reasonSource` | `{ id: string; title: string }`? | Optional viewed source article that best explains a `vector` recommendation                  |

**Reason Values:**

| Value    | Description                                       |
| -------- | ------------------------------------------------- |
| `vector` | Vector similarity recommendation                  |
| `random` | Random selection                                  |
| `hot`    | High popularity score (views, upvotes, favorites) |
| `title`  | Title similarity to source article                |
| `other`  | Other/fallback source                             |

### 5.2 GET /article/relevant/:id

Get articles relevant to a specific article.

**Request:**

- Path parameter: `id` (string) - Article ID

**Response:**

- 200: Array of relevant articles with `reason` field

### 5.3 GET /plaza/profile

Return the caller's recommendation interest profile, auto-generated persona/topic tags, semantic
interest clusters, category distribution, reading rhythm, favorite authors, and recent viewed
articles derived strictly from the subject's existing recommendation history.

**Request:**

- Uses the same `Authorization`, `X-Consent-Tracking`, and `X-Device-Id` headers and
  `resolveRecommendationSubject(ctx)` rule as `GET /plaza/get`.

**Behavior:**

1. Let `subject = resolveRecommendationSubject(ctx)`.
2. If `subject` is `null`, return HTTP 200 with `{ trackingEnabled: false, subjectKind: null, viewedCount: 0, retentionDays: 0, personaTags: [], topicTags: [], categories: [], clusters: [], favoriteAuthors: [], readingRhythm: [], recentArticles: [] }` without reading or writing any subject-specific Redis key.
3. If `subject.kind === 'user'` and `getConsentedDeviceId(ctx)` returns a device ID, complete `mergeDeviceHistory(deviceId, subject.userId)` before step 4.
4. Compute and return `RecommendationService.getInterestProfileSummary(subject)`:
    - Load `viewEntries = getBehaviorEntries(subject)` (newest first).
    - Hydrate viewed article IDs with one `ArticleService.getRecommendationArticlesByIds(ids)` call (metadata + preview only; deleted rows omitted; full `content` SHALL NOT be loaded).
    - Assign each hydrated entry at index `i` decay weight `config.recommendation.decayFactor^i`.
    - Partition the top `config.recommendation.profileSize` viewed IDs into up to 3 semantic interest clusters using the same clustering algorithm as `drawInterestProfiles` (at most one Chroma `get` request, degrading cleanly to `clusters = []` when Chroma is disabled or unavailable). Each cluster reports `{ label, weight, share, dominantCategory, keywords, sampleArticles }`.
    - Compute decay-weighted `categories`, `topicTags` (from explicit `article.tags` and curated OI/CS/Luogu keywords matched against title and summary, capped at 15), deterministic `personaTags` (capped at 6, each with factual `description`), `favoriteAuthors` (top 5), UTC+8 4-bucket `readingRhythm` (`morning` 06–11, `afternoon` 12–17, `evening` 18–22, `night` 23–05), and `recentArticles` (at most 8).
5. On unexpected error, log the error and return HTTP 500 with message `Failed to retrieve interest profile`.

### 5.4 DELETE /plaza/profile

Clear the caller's recommendation behavior and recommended history keys.

**Behavior:**

1. Let `subject = resolveRecommendationSubject(ctx)`.
2. If `subject` is `null`, return HTTP 200 with `{ cleared: false }` without touching Redis.
3. If `subject.kind === 'user'` and `getConsentedDeviceId(ctx)` returns a device ID, call `mergeDeviceHistory(deviceId, subject.userId)` before deleting the user subject's keys (preserving invariant 11).
4. Delete the subject's `behaviorKey` and `recommendedKey` in Redis and return HTTP 200 with `{ cleared: true }`.
5. On unexpected error, log the error and return HTTP 500 with message `Failed to clear interest profile`.

## 6. Recommendation Algorithms

### 6.1 getPersonalizedRecommendations(subject, count, excludedArticles)

**Algorithm:**

```
1. In parallel, fetch:
   a. viewEntries = getBehaviorEntries(subject)
   b. previouslyRecommended = getRecommendedArticles(subject)
   c. hotPool = ArticleService.getHotArticleIds(200)
   d. recentPool = ArticleService.getRecentArticleIdPool() (up to 3000 recent article IDs, cached 60s)
2. No private follow or saved-article data is read.
3. strictExcluded = Set(viewEntries.ids ∪ previouslyRecommended ∪ excludedArticles)
   hardExcluded   = Set(viewEntries.ids ∪ excludedArticles)
4. profileIds = selectProfileArticles(viewEntries, config.recommendation.profileSize)
5. interestProfiles = drawInterestProfiles(profileIds)
6. Build vectorPool:
   a. If interestProfiles is non-empty:
      - totalVectorBudget = min(180, count * 3 + min(strictExcluded.size, 150))
      - perClusterLimit = min(120, max(count * 2, ceil(totalVectorBudget / interestProfiles.length)))
      - Query EmbeddingService.getNearestArticleIdsBatch(interestProfiles.map(c => c.vector), perClusterLimit) in one batched Chroma request
      - Interleave cluster results in rank order, deduplicating by article ID
   b. Otherwise vectorPool = []
7. Let targetCount = count + min(10, max(5, ceil(count / 2))) (hydration buffer for deleted rows).
8. Build unseen ranked candidate lists excluding strictExcluded:
   a. vectorCandidates = vectorPool \ strictExcluded (preserving similarity rank)
   b. hotCandidates    = hotPool \ strictExcluded (preserving popularity rank)
   c. randomCandidates = unbiased Fisher-Yates sample of max(targetCount * 2, 40) IDs from (recentPool \ strictExcluded)
9. Mix candidate pools by target quota without destroying intra-pool rank order:
   a. If vectorCandidates is non-empty:
      quotas = { vector: ceil(targetCount * 0.6), hot: ceil(targetCount * 0.25), random: remainder }
      backfill order = [vector, hot, random]
   b. Otherwise:
      quotas = { hot: ceil(targetCount * 0.5), random: remainder }
      backfill order = [hot, random]
   c. Interleave selected items across pools proportionally while preserving relative order inside each pool.
10. Soft-recycle fallback: if step 9 produces fewer than count unique IDs, backfill up to targetCount from vectorPool, hotPool, and unbiased Fisher-Yates sample of recentPool excluding only hardExcluded (still never returning any ID in viewEntries or excludedArticles).
11. Hydrate selected candidate IDs via ArticleService.getRecommendationArticlesByIds (metadata + preview only; deleted rows omitted) and take the first count hydrated articles.
12. Record only the actually returned article IDs with recordRecommendedArticles(subject, returnedIds).
13. Add reason field from the first pool containing the ID, in the order vector, hot, random; fallback "other".
14. For returned items with `reason = "vector"`, attribute each item to a source viewed article from its recalling interest cluster:
    a. Fetch summary embeddings of those returned vector items in at most one `EmbeddingService.getVectors` call (degrading to empty map on failure/timeout).
    b. For each item, choose the cluster member article whose already-loaded viewed vector has the maximum cosine similarity to the item's embedding (ties keep earlier/more-recent order); if the item's embedding is unavailable, fall back to the recalling cluster's first (most recent) article ID.
    c. Load titles of the distinct chosen non-deleted source IDs in one `ArticleService.getArticleTitlesByIds` primary-key query (never loading `content`) and attach `reasonSource: { id, title }` when present.
15. Return filtered fields.
```

### 6.2 getPublicRecommendations(count, excludedArticles)

This algorithm is used when `GET /plaza/get` resolves no recommendation subject (section 3.1).

**Algorithm:**

```
1. In parallel, fetch:
   a. hotPool = ArticleService.getHotArticleIds(200)
   b. recentPool = ArticleService.getRecentArticleIdPool()
2. excludedSet = Set(excludedArticles)
3. Let targetCount = count + min(10, max(5, ceil(count / 2))).
4. Build candidate lists excluding excludedSet:
   a. hotCandidates = hotPool \ excludedSet (preserving popularity rank)
   b. recentCandidates = first max(200, count * 5) entries of (recentPool \ excludedSet)
   c. randomCandidates = unbiased Fisher-Yates sample of max(targetCount * 2, 40) IDs from (recentPool \ excludedSet)
5. Mix candidate pools by target quota without destroying intra-pool rank order:
   a. quotas = { hot: ceil(targetCount * 0.4), other: ceil(targetCount * 0.35), random: remainder }
   b. backfill order = [hot, other, random], then any remaining IDs in (recentPool \ excludedSet)
   c. Interleave selected items across pools proportionally while preserving relative order inside each pool.
6. Hydrate selected candidate IDs via ArticleService.getRecommendationArticlesByIds and take the first count hydrated articles.
7. Add reason field from the first pool containing the ID:
   a. "hot" for hotCandidates
   b. "random" for randomCandidates (when selected from the random pool)
   c. "other" for recentCandidates or any fallback source
8. Return filtered fields.
```

No Redis subject key is read or written by `getPublicRecommendations`.

### 6.3 getRelevantArticle(articleId, fromVector = 5, sourceArticle?, maxTitleMatches = 5)

**Algorithm:**

```
1. In parallel:
   a. similarIds = getSimilarArticles(articleId, fromVector * 3)
   b. article = sourceArticle ?? ArticleService.getArticleById(articleId)
2. Let originTitle = (article?.title || '').trim(), authorId = article?.authorId || 0.
3. In parallel, gather title candidates:
   a. authorArticles = authorId > 0 ? ArticleService.getArticleTitlesByAuthor(authorId) : []
   b. globalCandidates = originTitle.length > 0
      ? SearchService.searchArticleTitleCandidates(originTitle, max(maxTitleMatches * 6, 30))
      : []
4. Deduplicate candidates by `id` (excluding `articleId`), marking `sameAuthor = true` when the
   candidate came from `authorArticles` or has `authorId === article.authorId`.
5. Normalize both `originTitle` and `candidate.title` with `trim().toLowerCase().replace(/\s+/g, ' ')`.
   For each candidate:
   a. If either normalized title is empty, similarity = 0.
   b. Otherwise:
      - stringScore = string-similarity.compareTwoStrings(normOrigin, normCandidate)
      - levenshteinScore = max(0, 1 - levenshteinDistance / min(normOrigin.length, normCandidate.length))
      - similarity = max(stringScore, levenshteinScore)
   c. If similarity >= config.recommendation.relevantThreshold, record (candidate.id, similarity, sameAuthor).
6. Sort recorded title matches by similarity descending, then sameAuthor descending, then id ascending;
   take at most maxTitleMatches IDs as titleSimilarIds and initialize finalResult = [...titleSimilarIds].
7. Iterate simId in similarIds:
   a. If simId is not already in finalResult, append simId to finalResult and increment appendedCount.
   b. Stop when appendedCount >= fromVector.
   (Skipped duplicates SHALL NOT consume the fromVector budget.)
8. Hydrate finalResult via ArticleService.getRecommendationArticlesByIds (no full content load).
9. Add reason field: "title" if id is in titleSimilarIds, otherwise "vector".
10. Return filtered fields.
```

Meilisearch lookup failures or timeouts in step 3b SHALL degrade gracefully to `[]` without failing `getRelevantArticle`.

### 6.4 getSimilarArticles(id, count)

1. Get the article's embedding vector via `EmbeddingService.getVector(id)`.
2. If no vector (`null` or empty), return empty array.
3. Get `getNearestArticleIds(vector, count + 1)`.
4. Filter out the source article ID.
5. Return first `count` IDs.

## 7. Configuration

| Field                                 | Description                                     |
| ------------------------------------- | ----------------------------------------------- |
| `recommendation.anonymous.expireTime` | TTL for anonymous behavior data (seconds)       |
| `recommendation.anonymous.maxCount`   | Max behavior records per device                 |
| `recommendation.user.expireTime`      | TTL for registered-user behavior data (seconds) |
| `recommendation.maxHistory`           | Max behavior records per registered user        |
| `recommendation.profileSize`          | Max articles used to compute one profile vector |
| `recommendation.decayFactor`          | Weight decay for profile vectors `(0, 1]`       |
| `recommendation.relevantThreshold`    | Min title similarity for matching `[0, 1]`      |

## 8. Invariants

1. Personalized recommendations NEVER include articles in `viewEntries` or `excludedArticles`. Previously recommended articles are excluded whenever strict candidates provide at least `count` results; soft-recycle fallback applies only when strict candidates are exhausted.
2. Vector search requires Chroma to be enabled; otherwise returns empty results.
3. Profile and interest cluster vectors are decay-weighted by `decayFactor^i` and L2-normalized.
4. Recent articles have higher weight in profile calculation.
5. Title similarity uses the greater value of `string-similarity` similarity and guarded Levenshtein-derived similarity (`0` on empty titles), capped at `maxTitleMatches` ordered by descending similarity.
6. Public recommendations do not require a device ID.
7. Public recommendations do not read or write subject-specific Redis keys, `saved_article` rows, or `user_follow` rows.
8. `GET /plaza/get` excludes all parsed `exclude` article IDs from both personalized and public recommendation responses.
9. Recommendation candidate queries SHALL select article IDs only and SHALL NOT load article content. Recommendation hydration SHALL select metadata, `summary`, a bounded SQL preview `LEFT(content, 200)`, and `author` only, and SHALL NOT load full `mediumtext` `content`.
10. Hot recommendation ID pools SHALL be cached for 300 seconds and recent-pool recommendation ID pools SHALL be cached for 60 seconds. Random sampling SHALL draw from the cached recent pool per request using unbiased Fisher-Yates sampling rather than caching a fixed 20-ID subset.
11. For a request with a user subject, the system reads or writes `anon_behavior:*` and `anon_recommendations:*` only through `mergeDeviceHistory`.
12. `drawProfile` and `drawInterestProfiles` issue at most one Chroma `get` request per call. `getPersonalizedRecommendations` issues at most one batched Chroma `query` request per call and at most one Chroma `get` request for attributing the returned `vector` cards.
13. Vector candidate pools query `kind='summary'` vectors only and contain article IDs only; no chunk vector ID appears in a response or in a recommended key.
14. Interactive Chroma recommendation reads SHALL be bounded by a 3000 ms timeout; Redis or Chroma errors and timeouts in recommendation reads SHALL degrade gracefully (empty behavior / empty vector pool) rather than stalling or failing the request with 500.
